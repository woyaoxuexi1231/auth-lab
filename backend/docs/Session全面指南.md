# Session 全面指南

## 什么是 Session

Session（会话）指**服务器端为某个用户保存的一段"有状态"数据**：
用户登录后，服务器在内存、Redis 或数据库里开辟一块空间，记录"这个用户是谁、有什么权限、登录了多久"。
服务器只把一个随机的 **会话 ID** 交给浏览器，浏览器之后每次请求都带上它，
服务器拿着 ID 找回对应的会话数据。

```
浏览器                                   服务器
  │                                        │
  │  POST /login {user, pwd}               │
  │ ─────────────────────────────────────→ │
  │                                        │ 验证身份 → 创建 Session
  │                                        │   {userId, 权限, 过期时间}
  │  Set-Cookie: JSESSIONID=abc123         │
  │ ←───────────────────────────────────── │ 只把"房间钥匙"给浏览器
  │                                        │
  │  GET /profile                          │
  │  Cookie: JSESSIONID=abc123             │
  │ ─────────────────────────────────────→ │ 用钥匙找房间 → 身份恢复
```

> 一句话：**Session = 服务器端的"房间"，会话 ID = 房间钥匙**。
> Cookie 只是众多"递钥匙"的方式之一（详见第五章）。

## 一、概念的源头："会话"比 Web 老得多

### 计算领域的 Session（1960 年代起）

"会话"一词并非 Web 的发明。它来自更早的**分时操作系统**时代（1960 年代）：

- 一台主机供几十个终端使用，每个登录用户从登录到登出的一段连续时间被称为一次 **session（会话）**
- Unix 从诞生起就有会话的概念：登录记录（utmp/wtmp）、进程组与会话（setsid）
- 核心含义一直没变：**"一段有起止的、与某个用户绑定的交互过程"**

### Web 的困境：HTTP 是刻意无状态的

1989 年，Tim Berners-Lee 在 CERN 提出万维网；1991 年 HTTP/0.9 问世。
**无状态是 Berners-Lee 的刻意设计**，不是缺陷：

```
HTTP 的设计目标（1991）：
  简单 —— 一个 GET 请求就能取回文档，telnet 都能用
  可扩展 —— 服务器不需要记住任何客户端，天然扛得住大规模访问

代价：
  GET /page1 → 服务器：你是谁？
  GET /page2 → 服务器：你是谁？我不记得你
```

在文档分享时代这没问题。但当 Web 从"看文档"变成"用应用"（购物车、论坛、邮箱、登录），
"记住用户"成了刚需。**HTTP 协议本身至今没有任何会话机制**——它的替代者是应用层自己发明的。

> 有研究者把 Web Session 称为"技术史上最被广泛接受、最有用的补丁之一"——很贴切：
> 它是架在无状态协议之上的一层应用级补丁，不是协议的一部分。

## 二、Web Session 的诞生：没有单一发明者

与 Cookie（有明确的发明者 Lou Montulli）不同，**Web Session 没有一个明确的"发明者"**，
它是一群人在不同平台上的"平行发明"，只是形态高度相似。历史上有三条主线：

### 主线一：Cookie 出现之前（1991–1994）

Web 应用的早期先驱们不得不自己想办法传递状态：

| 方案        | 原理                          | 致命缺点                  |
|-----------|-----------------------------|-----------------------|
| URL 重写    | 把会话 ID 塞进 URL（路径或查询参数）      | 会泄露在日志、历史记录、Referer 里；链接被转发就泄露会话 |
| 隐藏表单字段  | 把会话 ID 藏在 HTML 表单的 `<input type=hidden>` | 只对表单提交有效，GET 链接无法携带      |
| Basic 认证  | 每个请求都带用户名密码                | 密码反复明文传输、无法登出             |

这些方案在 1994 年 Cookie 出现后逐渐退居二线——但**没有消失**：
它们至今仍作为"兜底方案"写在各平台规范里（见第五章）。

### 主线二：Cookie 接管"递钥匙"（1994 年之后）

1994 年 10 月，Netscape 在浏览器中引入 Cookie（详见 [Cookie 全面指南](Cookie全面指南.md)），
服务器端的"房间"（Session）与浏览器端的"钥匙"（Cookie）正式配对，**服务端会话模式就此定型**：

```
服务器创建 Session（存内存/文件/DB）→ 把随机 ID 放进 Cookie
浏览器保存 Cookie → 每次请求自动携带 → 服务器凭 ID 找回 Session
```

此后 30 年的服务端会话，本质都是这个模型。

### 主线三：平台级标准化（1996–2000）

各 Web 平台开始把会话管理写成规范，这是"谁的规范"问题的答案：

#### Java Servlet 规范 —— 影响最大的标准化

1996 年 Sun 推出 Java Servlet API，从一开始就定义了 `javax.servlet.http.HttpSession`；
此后在 Servlet 2.x 规范（J2EE 标准，第 7 章《Session Tracking》）中正式标准化。关键规定：

- **Cookie 方式**：容器必须通过名为 **`JSESSIONID`** 的 cookie 传递会话 ID（标准规定的名字）
- **URL 重写兜底**：客户端禁用 cookie 时，会话 ID 必须编码为路径参数 `jsessionid`
  （如 `http://host/catalog/index.html;jsessionid=1234`）
- **SSL 会话**：容器也可用 HTTPS 内建的会话机制跟踪
- **超时**：规范明确"HTTP 没有显式的结束信号，超时是判断用户不再活跃的唯一机制"
- **接口语义**：`getId()`、`getCreationTime()`、`getLastAccessedTime()`、
  `setMaxInactiveInterval()`、`invalidate()` —— 这些名字今天所有 Java 会话代码都在用

#### PHP —— 4.0 起内置

- **PHP 3.0（1998）没有内置会话**——当时被社区评为"最大的失望之一"，开发者只能靠第三方库（如 PHPlib）
- **PHP 4.0（2000）把会话内置进语言**：`session_start()` 开启会话，
  通过 cookie 发送随机会话 ID，服务器端写临时文件（`sess_<id>`）保存 `$_SESSION`
- PHP 的"零配置开箱即用"极大推动了 Web 会话的普及——当年的 LAMP 时代人人都在用

#### ASP / ASP.NET —— Session 对象

- 1996 年微软发布 ASP（随 IIS 3.0），提供 `Session` 对象（`Session("user") = ...`）
- 2002 年 ASP.NET 的 SessionState 支持内存、数据库（SQL Server）、进程外状态服务器等模式——
  是"会话可配置存储"的早期范本

#### 其他

Django（2005 起，数据库/缓存会话）、Ruby on Rails（2005，cookie store 与数据库会话）等框架
各自实现，但模型完全一致：**随机 ID + 服务端存储 + 超时**。

### 安全层面的"规范"：OWASP

会话安全没有 RFC，行业事实标准是 **OWASP Session Management Cheat Sheet**
（开放 Web 应用安全项目发布的会话管理指南），其中包含：会话 ID 必须不可预测、
必须用安全传输、登录后必须更换 ID（防会话固定）、设置合理超时等基准要求。
OWASP Top 10 长期把"破坏的认证与会话管理"列入最危险的十大问题。

### Session 的时间线

```
1960s  分时操作系统：登录-登出 = 会话（概念起源）
1991   HTTP/0.9：无状态协议（Berners-Lee，CERN）
1991–94 URL 重写 / 隐藏字段传递状态（早期方案）
1994   Cookie 问世（Montulli，Netscape）→ "钥匙"问题解决
1996   Java Servlet API：HttpSession 从第一版起进入 API
1996   ASP：Session 对象（微软）
1998   PHP 3.0 无内置会话（被批评）→ 2000 年 PHP 4.0 内置
2001   Servlet 2.3（JSR-53）：会话跟踪第 7 章正式标准化
2001+  SSO 兴起：CAS（耶鲁）、SAML（OASIS）
2005+  Web 应用框架（Django/Rails）内置会话中间件
2010s  分布式浪潮：会话复制 → Redis/memcached 集中存储
2015+  无状态 Token（JWT）对 Session 发起挑战
2020s  HttpOnly Cookie 重新受青睐（SPA 中存 Token 也用 Cookie）
```

## 三、工作原理

### 创建（登录）

```
① 用户提交用户名密码
② 服务器验证身份
③ 服务器创建 Session（分配不可预测的随机 ID）
④ 服务器把 Session 数据写入存储（内存 / 文件 / DB / Redis）
⑤ 响应头下发 Cookie：Set-Cookie: JSESSIONID=abc123; HttpOnly; SameSite=Lax
```

### 恢复（后续请求）

```
① 浏览器自动携带 Cookie: JSESSIONID=abc123
② 服务器从 Cookie 解析出会话 ID
③ 用 ID 查找 Session 数据
④ 读出登录状态 → 请求被"认出"
⑤ 请求结束：Session 数据保留（不销毁）
```

### 销毁（登出 / 过期）

```
① 用户点击登出
② 服务器使会话失效（invalid / destroy）：删除会话数据
③ 响应头下发过期 Cookie（Max-Age=0）让浏览器删除钥匙
④ 彻底登出
```

### 会话数据里的三个时间点

所有会话实现都记录这三个值（Java Servlet、PHP、Redis 结构大同小异）：

```
创建时间      creationTime          会话诞生时刻
最后访问时间   lastAccessedTime      每次请求都会刷新
最大不活动时间 maxInactiveInterval  超时阈值（如 30 分钟）

过期判定：lastAccessedTime + maxInactiveInterval < 现在 → 会话失效
```

## 四、会话 ID：房间里最值钱的东西

会话 ID 是身份的钥匙，攻击者拿到它等于拿到账号。因此：

| 要求       | 说明                              | 反例            |
|----------|---------------------------------|---------------|
| 不可预测     | 必须来自安全随机数（128 位+）              | 递增数字、时间戳     |
| 避免泄露     | 只走 HTTPS；不放 URL；日志脱敏             | 会话 ID 出现在 URL |
| 登录后更换    | 防会话固定攻击（攻击者预置 ID 诱导受害者登录）      | 登录复用旧 ID    |
| 定期轮换     | 高风险操作（改密、支付）后更换               | 全程同一个 ID     |

## 五、会话 ID 的传输方式

| 方式        | 原理                | 优点           | 缺点                 | 现状      |
|-----------|-------------------|--------------|--------------------|---------|
| Cookie    | 浏览器自动携带           | 自动、安全（可 HttpOnly） | 需处理跨域、SameSite 限制 | **主流**   |
| URL 重写    | ID 写在 URL 里        | 无 cookie 也能用     | 泄露、转发即丢          | 兜底方案    |
| 隐藏表单字段  | ID 藏在表单里          | 无需 cookie       | 仅表单提交有效           | 兜底方案    |
| 请求头（Token） | `Authorization: Bearer xxx` | 跨域友好、移动端友好     | 需客户端手动携带          | 移动端/API |

> 规范级事实：Java Servlet 规范把 Cookie 定为首选、URL 重写定为必须支持的兜底；
> RFC 6265（Cookie 规范）则是"钥匙传输"的正式标准。

## 六、存储方式的演进：一部 Web 规模扩张史

会话数据存哪里，直接反映了 Web 应用的发展阶段：

```
1990s  单机内存（HashTable）→ 重启即丢
  ↓
2000s  数据库 / 文件（支持持久化）
  ↓
2010s  内存缓存（memcached / Redis）→ 分布式共享 + TTL 自动过期
  ↓
2015+  无状态 Token（JWT）→ 干脆不存
```

| 存储方式 | 优点                    | 缺点                    | 适用阶段     |
|-------|-----------------------|-----------------------|----------|
| 内存    | 最快、零依赖                | 重启丢失、多实例不共享           | 单机/开发    |
| 文件    | 重启不丢                  | 慢、不共享、不易清理            | 早期 PHP   |
| 数据库   | 持久、可查、可管理             | 每次读写开销大               | 中小项目     |
| Redis/memcached | 快、分布式共享、TTL 自动过期     | 引入中间件依赖               | **生产主流**  |
| 无状态（JWT） | 无存储、天然分布式            | 无法主动踢人/权限实时生效        | 微服务/API  |

**关键演进动力**：一台服务器时代，会话存内存即可；当应用变成"几十台服务器 + 负载均衡"，会话必须"搬家"。

## 七、分布式场景的四个解法

```
问题：请求被负载均衡轮询到不同服务器，会话却只存在某一台上
      ┌────────────┐
浏览器 → 负载均衡 → │ 服务器A: 有 SessionX │
                 │ 服务器B: 没有 SessionX ← 又要求登录！
                 └────────────┘
```

| 方案       | 原理                            | 优点       | 缺点               |
|----------|-------------------------------|----------|------------------|
| 粘性会话    | 负载均衡把同一用户固定到同一台服务器         | 不用改应用代码 | 单点故障、扩容不均衡       |
| 会话复制    | 服务器之间互相同步会话（如 Tomcat DeltaManager） | 应用无感    | 网络开销大、节点多时爆炸     |
| **集中存储** | 会话统一放 Redis/memcached，所有服务器读同一份 | 干净、可靠、弹性 | 引入中间件；缓存挂了全掉线 |
| 无状态化    | 不用会话，状态放 Token（JWT）里        | 完全无共享   | 无法服务端踢人/实时改权限    |

> 演进路线：粘性 → 复制 → 集中存储（Redis 成为事实标准）→ 无状态化。
> 到 2026 年，"集中存储 + 会话"与"无状态 Token"两种路线并存，各占半壁江山。

## 八、并发控制：一个账号能登录几个地方？

| 策略     | 行为                     | 典型场景       |
|--------|----------------------|------------|
| 无限制    | 多端同时在线               | 通用 Web     |
| 单会话+踢旧 | 新登录生效，旧会话被踢下线       | 账号安全（银行类）  |
| 单会话+拒新 | 新登录被拒，旧会话保持          | 不允许重复登录    |

技术上就是"同一账号对应会话数上限 + 超限时淘汰策略"，各平台均有标准 API。

## 九、安全

| 攻击       | 原理                              | 防护                              |
|----------|---------------------------------|---------------------------------|
| 会话固定    | 攻击者预置自己的会话 ID，诱导受害者用其登录      | **登录成功后更换会话 ID**（各框架默认行为）        |
| 会话劫持    | 偷走会话 ID（XSS、抓包、日志泄露）冒充身份      | HttpOnly + HTTPS + 定期轮换           |
| CSRF     | 跨站伪造请求，浏览器自动带会话 cookie        | SameSite + CSRF Token              |
| 会话预测    | 猜出可预测的会话 ID                   | 安全随机数生成（128 位+）                   |

OWASP 会话管理基准（简化版）：不可预测的 ID + 仅 HTTPS 传输 + 登录后更换 +
合理超时 + 登出彻底失效（服务端删数据 + 客户端删 cookie）。

## 十、Session vs Token（JWT）

| 维度     | Session                    | JWT                     |
|--------|---------------------------|-------------------------|
| 状态    | 有状态（服务器存储）                | 无状态（Token 自带信息）          |
| 存储    | 服务器（内存/Redis）+ 客户端钥匙     | 客户端（localStorage/Cookie）  |
| 可撤销   | ✅ 删会话数据即失效                | ❌ 过期前一直有效（需黑名单）         |
| 权限实时更新 | ✅ 改会话数据立即生效               | ❌ 旧 Token 带旧权限           |
| 性能    | 每次请求查一次存储                 | 本地验签，零存储访问              |
| 跨域    | 依赖 Cookie 的跨域处理            | 请求头携带，天然跨域             |
| 适合场景  | 传统 Web、需要踢人/封号的业务           | 微服务、API、无状态架构           |

**选型**：要"服务端掌控"（踢人、封号、实时改权限）→ 有状态方案；
要"无状态可扩展"（微服务、第三方 API）→ Token。两者都完全正当，没有过时与否之分。

## 十一、Session 在今天：没有消失，只是换了位置

- **SSO 与身份提供商**：CAS（2001，耶鲁）、SAML、OAuth/OIDC——认证服务器保存的"登录态"本质就是会话
- **"忘记密码"的逻辑**：所有 Token 化系统里，"Token 可撤销"这个需求仍然指向有状态存储（黑名单、Refresh Token 存储）
- **SPA 时代的回归**：前端框架把 Token 存进 **HttpOnly Cookie** 已成最佳实践——
  "服务器下发、浏览器自动携带、JS 读不到"正是 Session 思想的精髓
- **会话还是会话**：从 1960 年代的分时终端到 2026 年的云原生应用，"一段与用户绑定的有状态交互"始终存在，
  变的只是存储介质和传输方式
